# 工作表截图周报生成

## 目标

读取用户上传的工作记录截图，完整还原目标周的记录，分类合并后直接输出可复制的 Markdown 周报。

只在当前会话交付结果。不要调用钉钉或其他业务连接器，不要创建日志、草稿、文件、JSON，不要发送外部消息。

## 输入字段

按以下列名识别表格；允许列宽、颜色、换行和少量名称差异：

1. 日期
2. 业务线
3. 客户/项目名称
4. 销售/对接人
5. 需求/问题
6. 工作内容

忽略筛选图标、单元格底色、水印和文字颜色。文字颜色仅是视觉样式，不代表额外状态。

## 截图读取规则

1. 逐张检查截图，按从上到下、从左到右的顺序读取所有可见行。
2. 多张截图存在重叠区域时，按日期、业务线、客户/项目名称和工作内容去重。
3. 日期单元格纵向合并或后续行留空时，沿用上方最近一个非空日期，直到出现新日期。
4. 其他空单元格保持为空，不要擅自继承上一行的业务线、客户或对接人。
5. 单元格内存在多行文字时，将其视为同一条记录的完整内容。
6. 不要因为客户/项目名称或工作内容为空而直接漏掉记录：
   - 业务线和客户/项目名称非空时必须保留。
   - 业务线非空，且需求/问题或工作内容任一非空时必须保留。
   - 只有样式、没有业务信息的空行可以忽略。
7. 无法可靠识别的局部文字标为 `[截图不清]`，不要猜测姓名、金额、产品名或结论。
8. 若用户指定日期范围，使用该范围；否则以截图中的最新日期确定所在自然周，并只整理该周。截图全部日期都属于同一周时，整理全部可见日期。
9. 若截图缺少关键列、关键区域被裁切或大面积模糊，先说明缺失位置并请用户补图；局部模糊不影响整体时，直接生成并标注待确认项。

在内部先整理为逐行记录并核对数量；除非用户要求，不要额外输出 OCR 中间表。

## 分类规则

遍历目标周的全部记录，同一条原始记录只归入一个位置。

- `阿里云` → **一、阿里-客户与项目**
- `百度云` → **二、百度-客户与项目**
- `专项-MaaS/聚合平台`、`专项-模型聚合平台`、`端木-Token Hub` → **三、专项 > 模型聚合平台**
- 其他以 `专项-` 开头的业务线 → **三、专项**；去掉 `专项-` 后作为子标题
- `售前团队` 中明确属于客户分层、存量客户或运营的记录 → **三、专项 > 存量运营**
- `售前团队` 中其他记录、`公司事项` → **四、其他工作项**
- 其他云厂商或未匹配业务线 → **四、其他工作项**；以业务线名称作为子标题

同一客户或项目的多条记录合并展示，合并时保留全部不重复的需求、工作内容、人名、金额和明确状态。多条工作内容按日期和截图中的先后顺序排列，使用中文分号 `；` 直接分隔；保持在同一行，不要使用“并”“以及”“同时”“另外”“并且”等衔接词，不要推断不同事项之间存在关联。

### 模型聚合平台

将相关记录分入以下互斥子块：

- **项目维护**：客户/项目名称非空。即使工作内容是模型新增、禁用或更新，也只能放在这里。
- **模型上新**：客户/项目名称为空，且内容明确涉及模型新增、上线、下线、禁用或更新。
- **平台维护**：客户/项目名称为空，且内容属于平台功能、账号、资质、供应商、费用、通道、测试、故障或其他平台级工作。

不要让同一条记录同时出现在多个子块。

平台维护条目必须以工作内容为主，不要以对接人姓名作为条目对象、标题或句首，不要使用“姓名：工作内容”的格式。截图中的对接人非空时，在工作内容描述完成后追加独立句式“对接人：姓名。”，并保持在同一条目、同一行；对接人为空时省略。不要把姓名改写进工作内容，不要遗漏截图中已有的对接人。

## 内容整理规则

### 客户与项目

阿里云和百度云条目使用：

```markdown
- **客户/项目名称（姓名）**
  - 总进度：20% / 50% / 80% / 100%
  - 时间：M.D 或 M.D-M.D
  - 需求/问题：原始需求的精炼合并
  - 进展：工作内容的精炼合并
```

项目标题的括号内只写姓名，不添加“销售”“对接人”等角色前缀；姓名为空时省略整个括号。客户/项目名称为空但记录有效时，使用“未注明客户/项目”，不要虚构名称。

按证据保守判断总进度：

- `100%`：明确已完成、已下单、已开通、已关闭，且没有未完成事项。
- `80%`：主要交付已完成，只待客户确认、验收、评审或最终结果。
- `50%`：正在实施、接入、迁移、测试、修复、申请或持续跟进。
- `20%`：需求收集、初步沟通、方案评估、询价或报价阶段。

同一项目包含多个事项时，以尚未完成事项中较低的阶段为准；所有事项均明确完成时才写 `100%`。证据不足时使用较低档，不要夸大进展。

要求：

- 保留原始记录中的人名、客户名、产品名、版本号、数量、金额和关键结论。
- 只有一条工作内容时，进展优先写成“动作 + 结果/当前状态 + 明确下一步”，不超过 100 字。
- 同一项目存在多条不同工作内容时，各事项精炼后使用中文分号 `；` 直接分隔并保持在同一行；不要换行，不要添加衔接词，也不要把无关事项改写成一个复合句。
- 工作内容为空但需求明确时，写“就{需求/问题}沟通对接中”。
- 业务线为阿里云、百度云、火山云或其他名称以“云”结尾的云厂商时，需求/问题为空统一写“业务上云”；其他业务线的需求/问题为空写“未注明”。除该固定默认值外，不要从工作内容反向编造需求。
- 不把计划写成已完成，不把待确认写成已确认。

### 专项与其他工作

专项和其他工作不强行补充百分比。使用“对象（姓名）：内容”的紧凑格式，括号内不添加角色前缀；对象或姓名为空时省略对应部分。同一对象的多条工作内容使用中文分号 `；` 直接分隔并保持在同一行，不添加衔接词。模型聚合平台的“平台维护”仍按前述特殊规则，以工作内容为主，不以姓名起句；存在对接人时，在条目末尾追加“对接人：姓名。”。

## 总结、计划和协助

### 本周工作总结

基于已识别记录概括 2–4 句，优先包含覆盖的客户/项目数量、已完成事项、进行中重点和主要风险。只能使用截图中的事实，不写空泛评价。

### 下周工作计划

生成 3–5 条编号计划：

- 仅从本周未完成、待确认、待修复或持续推进的事项保守延伸。
- 对进行中事项使用“跟进、推进、完成、验证”等动作。
- 对待确认事项使用“确认……结果”。
- 不纳入已明确完成、已下单、已开通且无后续动作的事项。
- 不编造新客户、新需求、新期限或截图中没有的承诺。
- 没有足够依据时写“暂无可从截图明确推导的下周计划”，不要凑数。

### 需协调与帮助

只提取截图中明确存在的阻塞、待客户确认、待商务确认、折扣/资质/权限依赖、故障或跨团队协作事项。没有明确事项时写“无”。

## 输出格式

直接输出以下 Markdown。不要输出处理过程、JSON、连接器说明或“草稿已创建”等提示。

```markdown
## 本周完成工作（YYYY.M.D-YYYY.M.D）

### 一、阿里-客户与项目

- **客户A（张三）**
  - 总进度：50%
  - 时间：7.21-7.23
  - 需求/问题：……
  - 进展：……

### 二、百度-客户与项目

- **客户B（李四）**
  - 总进度：20%
  - 时间：7.22
  - 需求/问题：……
  - 进展：……

### 三、专项

- **模型聚合平台**
  - **项目维护**
    - 客户C（王五）：……
  - **模型上新**
    - ……
  - **平台维护**
    - 完成供应商账号 Key 轮转及平台切换。对接人：蔡总。
- **产品专项**
  - ……

### 四、其他工作项

- **火山云支撑**
  - 客户D（赵六）：……

## 本周工作总结

……

## 下周工作计划

1. ……
2. ……

## 需协调与帮助

- ……
```

省略完全没有记录的一级章节和空子块。`需协调与帮助` 为“无”时直接写“无”，不使用空列表。
