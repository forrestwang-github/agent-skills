# 知识库 Markdown 规范

生成 Markdown 知识源文件时读取本文件。目标是同时满足：人在 Obsidian 中阅读和维护、未来大模型进行切块与检索、离开特定软件后仍可使用。

## 1. 文件角色

Markdown 是权威知识源。HTML、PDF、幻灯片或对话摘要均是派生阅读形式；发现冲突时回到 Markdown 和来源修订。

一份笔记应有一个清晰主题。若一章脱离母文后仍需要单独演进、被多处引用，或拥有独立来源体系，则它适合拆成原子笔记。大型主题使用“地图笔记”连接多个原子笔记，而不是无限加深单文件层级。

## 2. YAML 属性

使用以下稳定、扁平的 YAML；不要加入空字段，不要把大段正文塞进属性。

```yaml
---
title: 技术主题的规范名称
aliases:
  - 常见别名
tags:
  - tech/领域
  - knowledge/机制
type: technical-note
topic: 主题短名
status: seed
created: YYYY-MM-DD
updated: YYYY-MM-DD
source_quality: high
---
```

字段规则：

- `title`：唯一、稳定，避免“技术总结”“学习笔记”等泛称；
- `aliases`：只放真实别名、旧称或常用缩写；
- `tags`：少量层级标签，描述领域和知识类型，不把每个关键词都变成标签；
- `type`：默认 `technical-note`，地图笔记使用 `topic-map`；
- `status`：`seed`（初步建立）、`growing`（仍在补证据）、`verified`（核心结论已充分核验）；
- `created`、`updated`：ISO 日期；
- `source_quality`：`high`、`mixed` 或 `limited`，反映核心结论而不是来源数量。

Obsidian 属性适合小而原子的机器可读信息。复杂关系和证据说明放正文，不使用嵌套 YAML。

## 3. 正文骨架

结构随主题调整，但应覆盖以下知识功能：

```markdown
# 规范标题

> [!summary] 一句话定义
> 用一句完整的话说明它是什么，以及区别于相邻概念的关键特征。

## 先看结论

## 学习目标与范围

## 核心解释
### 本节要回答的具体问题

## 具体例子或过程演示

## 边界、代价与常见误解

## 实践判断或优化路径（按需）

## 相关概念与知识库连接

## 自测问题

## 来源与证据
```

“核心解释”内部使用所选报告模式的结构。不要为了对齐骨架保留空章节。

## 4. 面向学习的写法

- 先回答“为什么需要”，再介绍组成部分；
- 每个抽象概念给出最小充分解释，不用更多术语解释当前术语；
- 复杂流程使用具体输入逐步演示，步骤与真实机制一一对应；
- 公式先解释变量和直觉，再代入数值；
- 比较技术时统一比较口径，明确哪些是机制差异、哪些只是实现差异；
- 常见误解应说明错误推理发生在哪一步，而不只给“对/错”。

## 5. 面向 AI 检索的写法

- 每个 H2/H3 围绕一个明确问题，避免“其他”“补充”“更多”等无语义标题；
- 小节首段先直接回答标题中的问题，再展开推理；
- 小节尽量自足，使用明确技术名称，少用脱离上下文的代词；
- 重要定义和结论用自然语言完整复述，不只放表格或图片；
- 保持标题稳定，修订时不要仅为文风随意改名；
- 来源标记跟随事实，不集中到章末后让映射关系丢失；
- 代码、公式和表格前后补充解释文字，使纯文本切块仍能理解。

## 6. 事实类型标记

通常通过语句自然区分，必要时使用 Obsidian callout：

```markdown
> [!evidence] 已核验事实
> 由来源直接支持的结论。[S1]

> [!inference] 推导
> 基于哪些事实、经过什么推理、在哪些假设下成立。

> [!warning] 证据局限
> 来源冲突、版本未知或缺少可复现实验。
```

不要给每一段都加 callout。只在事实类型可能被误读时使用。

## 7. 知识库连接

在“相关概念与知识库连接”中分三类建议：

- **前置概念**：理解本文前应掌握；
- **相邻概念**：容易混淆、对比或共同使用；
- **下游主题**：建立本文认知后可继续学习。

若目标知识库已存在对应文件，使用 `[[笔记名]]`；不确定文件是否存在时，给出“建议链接”，不要假装链接已经可用。为跨工具兼容，核心正文不依赖 Obsidian 独有的块引用。

## 8. 来源清单

正文使用 `[S1]`、`[S2]`。文末按证据价值而非引用顺序堆叠说明：

```markdown
## 来源与证据

- [S1] **来源标题**｜机构或作者｜官方文档｜版本或日期  
  URL：<https://example.com>  
  检索日期：YYYY-MM-DD  
  支撑：本文关于……的定义和机制。
```

只有真正进入论证的来源才进入清单。延伸阅读与证据来源分开列示。

## 9. 自测问题

使用少量能够暴露理解缺口的问题，覆盖：

- 用自己的话解释核心机制；
- 给定一个具体输入，预测过程或结果；
- 判断一个边界条件是否会使结论失效；
- 区分一个容易混淆的相邻概念；
- 将机制应用到一个新场景。

默认不直接给答案；若用户需要复习卡片，再单独生成答案或问答卡。
