## 交互原则

- 先展示第一层；第二层按精度需要展开；第三层默认收起。
- 每个展示字段都给出：通俗名称、是什么、影响什么、示例、是否必填、推荐值/选项和推荐理由。
- 只询问缺失且可能改变 GPU 卡数、精度、拓扑、部署框架或基础资源的字段。
- 需要追问时一次性列出全部高影响问题；不要分多轮零散索取已知字段。
- 不询问“是否为私有权重或二次量化权重”。默认按用户指定的公开模型和精度处理；只有制品与公开版本不一致时才要求实际制品参数。


## 第零层：模型 ID 后的需求收集门槛

当用户只提供模型 ID 时，先回复“已收到模型 ID，但还不能可靠确定部署规模”，并一次性收集以下信息。每一项后必须同时写明“为什么需要/会影响什么”和“建议值/建议理由”，让用户可以直接按建议值确认：

| 需要补充的信息 | 为什么需要、会影响什么 | 建议值与理由 |
|---|---|---|
| 典型活跃并发 | 决定经济型副本的 KV/状态池和常态吞吐 | `8`；适合作为没有历史监控数据时的保守起点 |
| 峰值活跃并发 | 决定生产型副本的峰值 KV/状态池和总吞吐 | `32`；覆盖中小规模内部服务的初始峰值，必须用监控修正 |
| 每日峰值持续小时 | 说明峰值资源的日均闲置程度，不直接减少峰值卡数 | `1` 小时；用于区分偶发峰值与长时间高负载 |
| 典型/最大输入 Token | 影响 Prefill、KV Cache 和长上下文显存 | 典型 `2048`、最大 `32768`；前者接近常见对话，后者用于长请求安全校验 |
| 典型/最大输出 Token | 影响 Decode 时长、KV Cache 和公网用户接入带宽 | 典型 `512`、最大 `4096`；覆盖普通回答及较长回答 |
| 最大长度同时并发数 | 决定极端长请求是否跨越 GPU 卡数边界 | 不清楚时按 `1–峰值并发` 给区间；不能假定所有峰值请求都是最大长度 |
| P95 首 Token 时延（TTFT） | 决定 Prefill 性能下限和单副本是否需要更多 GPU | `2000 ms`；适合作为交互服务的初始门槛，严格业务应提供实际 SLO |
| 单请求输出速度 | 决定 Decode 性能下限和用户体验；内部换算 ITL | `30 Token/s`；约等于 `33.3 ms/Token`，便于交互体验评估 |
| 精度策略 | 影响权重显存、KV 显存、量化 kernel、效果和框架兼容性 | 默认 `preserve` 使用模型推荐精度；优先稳定性，不把未验证量化当成确定方案 |
| GPU/节点边界 | 决定候选型号、单机/多机拓扑和是否需要 RDMA | 不限硬件、优先单节点；减少跨节点通信变量，便于初次落地 |
| 输入形态 | 图片/视频会增加视觉编码器显存、CPU 预处理和公网用户接入流量 | 默认纯文本；若使用多模态，必须补图片数量/分辨率或视频时长 |
| 故障能力 | 决定副本数、总 GPU 和故障后的服务能力 | 默认双副本 active-active，但允许单副本故障后降级；若要保持完整峰值需额外加副本 |
| 公网典型/峰值到达 RPS | 决定公网入向峰值；并发反推值不能代表用户突发请求 | 有监控时填写入口/API 网关 P95–峰值到达率；没有则先不输出精确公网带宽 |
| 响应方式与峰值完成 RPS | 决定公网出向公式；流式看活跃流与 Token/s，非流式看响应完成速率 | 默认流式；非流式补充典型/峰值响应完成 RPS，避免把平均吞吐当突发带宽 |

如果用户未提供硬件边界，进入自动选型模式：先计算每推理副本的客观显存需求，再以默认“优先单节点、最多 8 卡/节点、TP/PP 可取 1/2/4/8/16/32/64”生成多卡候选；用户提供现有硬件时才进入兼容性评估模式。RPS 可由并发和请求时长推导为推理容量代理，但不得用于公网突发带宽。模型 ID、revision、架构、参数、上下文、权重大小和框架兼容性优先由官方资料核实，不要求用户手填。
## 第一层：核心输入

| 字段 | 是什么 | 影响什么 | 示例 | 必要性 |
|---|---|---|---|---|
| 模型 ID 与 revision | 要部署的准确模型和固定版本 | 参数、权重大小、上下文、算子及兼容性 | `org/model@commit` | 必填；revision 可先缺省，交付前必须固定 |
| 典型输入 Token | 正常繁忙时单请求常见输入长度 | 常态 Prefill 算力和 KV cache | 2,000 | 必填 |
| 最大输入 Token | 允许的最长输入 | 极端显存和长上下文风险 | 32,000 | 必填 |
| 典型输出 Token | 正常回复的常见生成长度 | Decode 吞吐和请求持续时间 | 500 | 必填 |
| 最大输出 Token | 单请求最长回复 | 极端 KV cache 和占用时间 | 2,000 | 必填 |
| 典型活跃并发 | 正常繁忙时引擎内同时推理的请求数 | `economic` 的 KV cache 和吞吐 | 16 | 必填 |
| 峰值活跃并发 | 高峰时同时推理的请求数 | `peak_production` 的卡数和副本数 | 64 | 必填 |
| 每日累计峰值小时 | 每天所有峰值时段合计持续多久 | 解释峰值方案的闲置程度，不直接减少峰值卡数 | 1.5 小时 | 必填 |
| P95 TTFT | 95% 请求从提交到首 Token 的最长时间 | Prefill 性能下限 | 2,000 ms | 要求准确卡数时必填 |
| 单请求 Token/s | 单个活跃请求每秒生成的 Token 数 | Decode 速度和用户体验 | 30 Token/s | 要求准确卡数时必填 |
| 量化接受策略 | 是否允许用低精度降低显存与卡数 | 权重大小、兼容性和效果验证 | 保持原精度 | 必填选择 |

量化接受策略只给三个通俗选项：

1. `preserve`：保持模型原始推荐精度。
2. `validated_only`：只接受已经通过业务效果验证的量化。
3. `cost_first`：允许优先降低 GPU 数量，但必须补做效果与兼容性验证。

只收集单请求 Token/s，内部换算：

```text
derived_target_itl_ms = 1000 / target_output_tps_per_request
```

不要再要求用户同时输入 P95 ITL。

## 第二层：精度增强

这些字段默认可跳过；缺失时可估算，但必须标记假设和置信度。

| 字段 | 是什么 | 影响什么 | 何时追问 |
|---|---|---|---|
| 典型/峰值到达 RPS | 每秒新到达服务入口的请求数 | Prefill、Decode 总吞吐及公网入向峰值 | 需要计算公网带宽或入口存在突发时 |
| 非流式典型/峰值响应完成 RPS | 每秒完成并向用户发送完整响应的请求数 | 非流式公网出向峰值 | 响应不流式返回时必须提供 |
| 响应方式 | 流式逐段返回，或非流式完整返回 | 决定公网出向的计算模型 | 公网或云上服务需要计算带宽时 |
| 最大长度同时并发数 | 同时达到最大上下文的请求数 | 极端 KV cache 上界 | 最大长度上界跨越 GPU 卡数边界时 |
| 多模态输入规模 | 每请求图片数量/分辨率、音视频时长 | 编码器显存、预处理 CPU 和吞吐 | 模型接收图片、音频或视频时 |
| 多模型/多 LoRA 共存数 | 同时驻留或动态切换的模型/适配器数 | 权重显存、内存和加载时间 | 明确存在共存需求时 |

RPS 缺失时可由并发和请求持续时间估算，用于推理容量交叉校验；该值不是实测公网到达率，不能用于配置公网突发入向带宽。流式输出的公网出向还需单请求 Token/s；非流式输出必须取得响应完成 RPS，或先由网关监控和压测补齐。

## 第三层：高级部署约束

默认收起并提供推荐选项。用户不指定时由 Skill 计算，不把工程参数转嫁给售前使用者。

| 条件 | 推荐选项 | 其他选项 | 配置影响 |
|---|---|---|---|
| GPU 范围 | 自动选择 | 指定厂商、型号或排除项 | 限制候选和软件生态 |
| 推理引擎 | 自动选择 | vLLM、SGLang、TensorRT-LLM、其他 | 算子、量化、并行和性能 |
| 节点策略 | 优先单节点，必要时多节点 | 仅允许单节点 | 单副本最大卡数和 RDMA |
| 单节点 GPU 上限 | 自动 | 1/2/4/8/自定义 | TP 上限和节点数 |
| 可用性 | 双副本，故障时允许降级 | 单副本；故障后仍满足完整峰值 | 副本数和总 GPU |
| CPU Offload | 关闭 | 允许 | 降低 GPU 显存压力但增加内存、数据传输和延迟风险 |

以下由 Skill 推荐，通常不询问用户：

- 权重与 KV Cache 的具体 FP16/BF16/FP8/INT8 格式；
- vLLM、SGLang 或 TensorRT-LLM；
- TP、PP、DP；
- Continuous Batching；
- Prefix Cache；
- Speculative Decoding；
- 节点内互联与跨节点 RDMA；
- CPU、内存、存储和公网用户接入带宽。

## 未知模型处理

默认处理公开可核实的模型，不限制许可证类型。查询不到模型或指定 revision 时，一次性索取：

- Dense/MoE 架构、总驻留参数；MoE 另给激活参数；
- 权重精度、量化格式和实际模型制品大小；
- 层数、KV Head 数、Head Dimension；
- 原生最大上下文；
- `config.json`、模型卡、技术报告或厂商技术文档；
- 已验证的推理引擎、自定义代码和算子要求。

若模型使用 MLA、CSA、HCA 或其他特殊注意力，还需官方 KV cache 计算说明、引擎实现数据或运行时显存测量。不能取得时只输出区间。

## 不作为常规输入的字段

- P50/P99 延迟：首版以 P95 SLO 规划，不显著改变基础资源口径。
- 完整输入输出概率分布：精度收益有限，收集成本高；用典型值、最大值和最大长度并发替代。
- 未来半年增长率：属于扩容路线，不决定当前模型单副本资源。
- 前缀重复率：只有明确评估 Prefix Cache 时再收集。
- 用户总数、日请求量：不能直接反映同时活跃负载。
- 全天平均并发：会被夜间空闲稀释；改用典型活跃并发。
- 请求排队长度：是运行策略和观测结果，不是硬件基础输入。
- 集群总输出 Token/s：可由并发/RPS、输出长度和单请求 Token/s 推导并交叉校验。
- 公网用户接入载荷、请求报文大小：由 Token 数、响应方式和工程系数估算；公网峰值到达/完成 RPS 应从入口监控或压测取得。

## 信息不足处理

1. 只有模型 ID 时，先追问第零层字段，不生成两档精确部署方案。
2. 如果用户只问显存下限，可不要求性能 SLO，但仍需模型结构、权重制品和精度信息；特殊注意力还需 KV bytes/token。
3. 如果用户要求准确卡数或性能达标，典型/峰值负载、TTFT 和单请求 Token/s 不得全部缺失。
4. 用户不能补充时，给出场景区间或资源下限，不输出单一精确值；每个区间写清对应假设。
5. 缺失模型结构、精度兼容性或最大长度并发导致卡数边界不确定时，将置信度设为 `low`，若跨越 GPU 卡数边界则明确要求补充或压测。
6. 每项假设说明它对 GPU 数、拓扑、框架或性能结论的影响。
