## 基础目录边界

`gpu-catalog.json`只缓存相对稳定的硬件事实：

- 厂商、精确型号、形态、架构和显存版本；
- 显存容量/类型/带宽；
- 官方明确支持的精度；
- 稠密与稀疏理论算力（分开保存）；
- PCIe、NVLink/NVSwitch、Infinity Fabric、MetaXLink 等互联；
- 功耗、MIG/虚拟化能力；
- 官方直接来源、访问日期和 final/preliminary 状态。

不要把以下内容写成 GPU 固定属性：

- 某模型 Token/s、TTFT、ITL 或固定卡数；
- 推理框架/模型兼容性；
- 云实例 SKU、库存、价格或区域；
- 出口限制、禁售或团队可售性。

通过脚本查询，不要读取完整目录：

```text
model-private-skill gpu filter \
  --min-vram-gb <单卡显存下限> \
  --precision <BF16|FP16|FP8|INT8> \
  --max-results 5
```

脚本结果只是硬件初选，不能直接成为最终候选。

## 硬性筛选

先定义厂商中立要求：

- 单卡最低标称显存；
- 每副本所需总显存、每副本卡数和单节点卡数；
- 所需权重/KV 精度和量化 kernel；
- 模型格式、特殊算子和引擎兼容性；
- 节点内互联；
- 是否跨节点及 RDMA 证据；
- 单副本最大节点数。

最终候选必须同时满足：

```text
硬件精度支持
AND 单卡与总显存满足
AND 模型/格式/算子兼容
AND 引擎支持所需并行度
AND 节点及互联满足
```

目录字段不完整或兼容性没有一手证据时，只能标记为“待验证硬件线索”，不得作为确定性候选。

## 候选排序

按以下顺序排序，不使用价格或库存：

1. 有同模型、同精度、同引擎、相近负载的性能基准；
2. 能满足 TTFT 和单请求 Token/s；
3. 单副本可留在单节点；
4. 每副本 GPU 更少；
5. 总节点更少；
6. 显存余量合理，避免明显不足或严重浪费。

最终每档最多 3 个参考型号。同一方案中的替代型号必须采用相同卡数和拓扑；需要不同卡数时拆成独立方案或明确为拓扑变体。

## 联网复核

联网前必须完整读取并执行[证据来源策略](source-policy.md)。以下步骤中的“官方”均以该策略的发布者身份、来源类型和直接证据要求为准。

只对最终 1–3 个候选联网核实：

1. 打开 GPU 厂商 Datasheet 或官方规格页，核对精确形态和显存版本。
2. 打开引擎官方支持文档/仓库，核对模型、精度、量化 kernel、自定义算子和并行支持。
3. 查找 exact 性能基准；不存在时查一次官方 similar 基准。
4. 仍不存在时停止搜索，保留容量候选，性能标记 `benchmark_required`。
5. 为每个结论记录 `evidence_id`、直接 URL、访问日期、版本及匹配等级。

理论 FLOPS/TOPS 不能换算为保证性 Token/s。非 CUDA 或国产加速器必须单独验证模型、算子和引擎；“生态兼容”营销表述不等于具体模型已兼容。

## 目录维护

- 正式规格每 90 天复核一次。
- 新 GPU 发布后及时新增。
- `preliminary` 项每次使用前重新核实。
- 同名不同形态或显存版本必须拆成不同记录。
- 模型、引擎和性能信息每次动态查询，不随 GPU 固定目录一起维护。
- 官方资料冲突时保留冲突说明并降低置信度，不覆盖原始证据。
