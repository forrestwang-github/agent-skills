# 技术学习与知识库报告

本技能服务于个人技术学习。首要目标是帮助用户建立准确、可解释、可复用的技术认知；结构化格式用于长期维护、关联和机器检索，不为排版而牺牲理解。

默认把 Markdown 视为知识源文件，兼容 Obsidian 和通用文本工具。HTML 是可选阅读版，不是知识的唯一载体。不要假定用户已有资料：只有技术名词也可以从可靠来源开始研究。

## 输出位置与 Obsidian 配置

开始生成文件前，若 [config/vault.yaml](config/vault.yaml) 存在，先读取其中的工作区与 Vault 配置。

**默认只写入使用本技能的当前项目工作目录**：

- Markdown 写入 `<workspace_note_root>/<技术领域>/<规范标题>.md`；
- HTML 阅读版写入 `<workspace_html_root>/<技术领域>/<规范标题>.html`；
- 主题地图若需要，写入 `<workspace_note_root>/知识地图/<主题名称>.md`。

只有用户在当前请求中明确要求“保存到 Obsidian”“同步到 Obsidian”或“复制到 Obsidian”时，才在项目目录完成生成与验证后，将对应成品再复制一份到配置的 Vault：

- 主题地图复制到 `<obsidian_map_root>/<主题名称>.md`；
- Markdown 知识笔记复制到 `<obsidian_note_root>/<技术领域>/<规范标题>.md`；
- 已生成的 HTML 复制到 `<obsidian_html_root>/<技术领域>/<规范标题>.html`。

仅仅提到“知识库”“Obsidian 兼容格式”或“以后放进 Obsidian”不构成复制授权。用户明确指定其他输出路径时，按指定路径生成；若同一请求还明确要求复制到 Obsidian，再执行复制。

复制到 Vault 时不修改 `.obsidian`，不移动已有笔记，不自动重构目录。写入前检查同名文件：明确是同一知识主题时先读取并比较后更新；无法确认时停止复制并说明冲突，不覆盖。来源与证据默认写在知识笔记正文，不另建重复来源笔记。

文件名使用稳定的技术名称并移除 Windows 非法字符。领域目录优先复用已有分类；没有合适分类时才创建语义明确的新目录，避免为单篇笔记建立过细层级。

## 判断是否使用

以下情况使用本技能：

- 用户想系统理解某项技术，而不是只要一句定义；
- 用户要梳理原理、因果链、演进路线、影响因素、收益边界或优化优先级；
- 用户要把一份或多份材料整理为可长期维护的技术知识；
- 用户明确要求知识库笔记、深度报告、Markdown 或 HTML 技术文档。

以下情况直接用通用能力：快速定义、局部事实查询、代码实现、故障处理，或用户明确只要简短回答。

不要机械追问交付格式。用户未指定时，默认输出一份规范 Markdown 知识笔记；明确要求 HTML 时，同时保留 Markdown 源文件并生成 HTML 阅读版。只有主题存在实质歧义、目标读者水平会改变解释路径，或多个范围选择会显著改变结果时，才先询问。

## 工作原则

1. **理解优先**：先建立问题、机制和因果关系，再决定章节与视觉形式。
2. **证据分级**：事实强度不得超过证据强度；来源冲突、不确定性和推导必须显式标注。
3. **原理自足**：正文不能依赖“见附件”“详见链接”才能成立；链接用于核验和延伸。
4. **连续可读**：术语先定义后使用，章节之间说明承接关系；避免名词和要点堆砌。
5. **检索友好**：每个小节围绕一个可独立回答的问题，开头先给直接结论，并保留稳定标题、明确主语和来源标记。
6. **结构适配内容**：不要为了满足固定数量而凑因素、章节、例子或来源。

## 执行流程

### 1. 界定学习问题

根据用户输入写出内部研究框架：

- 要理解的对象是什么，不是什么；
- 用户最终应能解释、判断或应用什么；
- 哪些前置概念不可缺少；
- 主题更适合“机制学习”“演进链”“因素分析”还是混合结构。

信息足够时直接研究。若用户只给一个明确技术名词，默认从概念、问题背景、核心机制、具体过程、边界与关联技术展开，不要求用户补材料。

### 2. 研究与建立证据账本

有用户材料时先完整提取并理解，但不要把它视为天然正确或唯一来源；同时按可靠性补充、核验。没有材料时，从权威来源主动研究。

开始研究前读取 [references/research-and-evidence.md](references/research-and-evidence.md)，按其中的来源层级、交叉核验、数字和推导规则建立证据账本。核心规则：

- 优先标准、规范、官方文档、原始论文、源代码或维护者材料；
- 关键机制尽量回到一手来源；重要或有争议的结论应交叉核验；
- 可以计算、比较和推导，但必须给出公式、输入、假设与结论边界；
- 无法充分核验的内容可保留为“有限证据”“推断”或“待核验”，不能伪装成事实；
- 对可能变化的信息记录版本或检索日期。

### 3. 建立解释模型

成文前先形成一条最短但完整的解释链：

`它解决什么问题 → 输入和约束是什么 → 内部机制怎样运行 → 为什么产生该结果 → 在什么条件下失效或不划算 → 与相邻技术如何区分`

晦涩机制紧跟一个严格对应的具体例子，使用真实输入或简化数值逐步演示。例子用于复现机制，不用文学化类比替代机制。

### 4. 选择报告模式

按主题组合内容，不强制所有章节出现。详细结构读取 [references/report-patterns.md](references/report-patterns.md)。

- **机制学习模式**：概念边界 → 问题背景 → 前置知识 → 机制分步 → 实例演算 → 性能与边界 → 相邻概念。
- **演进链模式**：每一环按“旧问题 → 新方案 → 机制 → 效果 → 新矛盾”展开，使下一环回应上一环。
- **因素分析模式**：指标口径 → 收益与反噬边界 → 因果分层 → 候选因素与筛选 → 关键因素 → 优化优先级。
- **混合模式**：以一个主模式组织正文，其他模式只补充主线，不平行堆叠多套框架。

因素分析不再预设 15—20 项。候选因素以覆盖完整因果链为准，并明确标注：保留、并入或排除；用户提出的伪因素必须解释其为何不成立。优化动作若存在，逐条给出成本和必要性：

- 成本：低＝配置或局部代码；中＝明显工程开发或跨团队协作；高＝架构、迁移或硬件投入。
- 必要性：必做＝否则其他收益明显被稀释；建议＝多数适用场景净收益为正；视情况＝依赖特定流量、规模或约束。

### 5. 生成知识源文件

读取 [references/knowledge-note-spec.md](references/knowledge-note-spec.md)，生成 Obsidian 友好的 Markdown：

- 使用稳定 YAML 属性和唯一 H1；
- 顶部提供结论、学习目标和适用边界；
- 核心事实就近使用 `[S1]` 形式标注来源；
- 将“事实、推导、经验判断、未知项”分开表达；
- 结尾包含相关概念、知识库链接建议、自测问题和来源清单；
- 核心知识不能只存在于表格、图片或 HTML 中。

按“输出位置与 Obsidian 配置”的规则，先把文件写入当前项目工作目录。只有用户明确要求复制到 Obsidian 时，才检查 Vault 中的真实笔记并补充可用的 `[[内部链接]]`；不存在的关联概念只列为建议链接，不创建空白占位笔记。

如果主题已经大到包含多个可独立复用的概念，先输出一份地图笔记，再按用户要求拆成原子笔记；不要未经请求一次生成大量零散文件。

### 6. 按需生成 HTML 阅读版

仅在用户明确要求 HTML、深度报告或可视化阅读版时，读取 [references/html-report-spec.md](references/html-report-spec.md)，基于 Markdown 的同一知识内容生成单文件 HTML。HTML 必须：

- 内嵌 CSS、无外部运行依赖、可离线打开和打印；
- 含固定于左上角的常驻目录，目录链接与真实章节锚点对应；
- 正文与 Markdown 在结论、数据、来源和边界上保持一致；
- 卡片只用于真正需要聚合的结论或因素，不把整篇文章切成碎片。

### 7. 验证

对所有交付文件运行：

```text
python scripts/validate_artifact.py <笔记.md> [报告.html]
```

脚本通过只是最低门槛。随后人工复查：

- 读者能否在不打开来源的情况下复述核心机制；
- 每个重要数字、版本事实和争议结论是否有合适证据；
- 推导是否展示输入和假设；
- 术语是否首次出现即定义，简称是否给出中英文全称；
- 是否存在脱离上下文的“它、这个、上述”、对话残留或版本性词汇；
- 章节是否围绕学习问题推进，而不是围绕搜到的资料排列；
- Markdown 是否适合拆分、链接和机器切块；HTML 目录、窄屏与打印是否正常。

## 交付说明

简要说明：生成了哪些文件、研究范围、证据局限、仍待确认的问题，以及建议加入知识库的相关概念链接。不要把“来源多”描述成“结论一定正确”。
