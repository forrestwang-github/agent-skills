# 技术报告结构模式

成文前读取本文件，根据学习问题选择一个主模式。结构是解释工具，不是必须填满的模板；任何章节若不能推进理解，应删除或合并。

## 通用开头

所有模式建议从以下内容开始：

1. **一句话定义**：对象是什么，以及最关键的区别特征。
2. **先看结论**：3—6 条真正影响理解或决策的结论。
3. **学习目标**：读完后能够解释、判断或完成什么。
4. **范围与边界**：本文讨论的版本、层级和不覆盖内容。

## 模式 A：机制学习

适用于“X 是什么”“X 为什么有效”“讲透 X”。

建议顺序：

1. 要解决的原始问题；
2. 必要的前置概念；
3. 输入、状态、约束和输出；
4. 机制逐步运行；
5. 一个可手工跟随的实例；
6. 为什么会得到该结果；
7. 性能、正确性和工程代价；
8. 失效条件与不适用场景；
9. 与相邻或易混技术的区别；
10. 实践判断或进一步学习路径。

抽象机制的实例必须逐步对应真实过程。例如解释注意力时，可使用少量词元和简化向量展示投影、打分、归一化与聚合；不能只用“聚光灯”类比代替计算。

## 模式 B：技术演进链

适用于“X 如何演进”“把一组技术串起来”“为什么先有 A 后有 B”。

先确定主轴，例如“降低内存访问”“扩展上下文”或“提高故障容忍”，避免按资料顺序编年。每一环固定回答：

1. 上一代方案留下了什么问题；
2. 新方案改变了哪个关键变量；
3. 机制如何实现；
4. 得到了什么效果，证据是什么；
5. 又产生了什么新矛盾。

下一环应回应上一环的新矛盾。若某项技术与主轴没有因果承接，放入“正交技术”或“相关分支”，不要强塞进主线。时期与代表系统属于事实，需引用可核验来源。

结尾给出演进谱系表：阶段、核心问题、关键机制、主要收益、新代价、代表实现。

## 模式 C：因素分析与优化

适用于“什么影响 X”“怎么提高 X”“哪些投入最值得”。

### 指标和收益

先定义分析对象、分子分母、时间窗口和观测层级。解释指标改善如何传导到成本、延迟、吞吐、质量或风险，并正面回答“过度优化是否反噬”。指标本身与工程取舍分开讨论。

### 因果分层

从底层约束到上层行为建立完整链路，例如：资源 → 执行引擎 → 算法或模型 → 平台调度 → 应用工程 → 流量。层次根据主题重建，不照搬示例。

### 候选因素筛选

候选因素数量由因果覆盖决定。表格使用：

| 因素 | 所属层 | 作用机制 | 证据强度 | 去向 | 理由 |
|---|---|---|---|---|---|

去向只有：

- **保留**：影响重要且机制独立，需要深入解释；
- **并入**：实质上是另一因素的子项或表现；
- **排除**：缺乏因果路径、影响可忽略或不属于当前口径。

用户点名但不成立的因素必须显式解释，不能静默删除。

### 关键因素

每个保留因素回答：

1. 它改变了因果链中的哪个变量；
2. 为什么方向和幅度会如此；
3. 哪些边界条件会改变结论；
4. 有哪些可执行动作；
5. 动作的成本、必要性、依赖和可观测验证指标。

路线图按投入回报和依赖组织，不强制恰好三阶段。常见顺序是：测量与口径治理 → 低成本确定性改进 → 工程建设 → 架构投资。

## 模式 D：多材料整合

适用于把文档、论文、笔记或网页整合为一个知识主题。

先建立概念对照表，识别：重复内容、术语异名、版本差异、事实冲突、因果错位和缺失环节。只在以下情况请求用户决策：

- 材料对应不同技术对象或版本，无法合理合并；
- 是否保留某个分支会显著改变篇幅或主线；
- 内部材料与公开权威来源冲突，且用户语境决定取舍；
- 目标是忠实整理原文，而不是建立当前正确的知识。

不存在这些分歧时，直接整合并在交付说明中报告修正与证据局限，不强制经过“汇报发现—审大纲—再成文”的多轮流程。

## 通用写作纪律

- 每章开头先说本章要解决的问题以及它与上一章的关系；
- 正文以连贯原理叙述为主，列表用于并列项和检查项；
- 简称首次出现写中文全称、英文全称和简称，之后再用简称；
- 中文正文可以保留必要的英文正式名称、代码、接口和行业惯用词，避免无意义的英文夹杂；
- 对非主线但必要的概念使用就近注解，不让附录承担主线解释；
- 不使用“终稿、修订版、刚才、你上传的、见上文截图”等对话或版本性表述；
- 核心结论不能只出现在 TL;DR、表格、图或卡片中，正文必须解释。
