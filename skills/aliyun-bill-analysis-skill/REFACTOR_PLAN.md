版本：1.0  
状态：v2 核心改造已实施  
适用对象：云服务商内部售后人员  
主要场景：对客户导出的历史账单进行一次性、快速、准确的结构化分析

## 1. 定稿结论

本 Skill 定位为“确定性账单分析工具”，不是“云资源优化决策工具”。

核心任务：

1. 从数万行阿里云原始账单中识别客户使用的产品；
2. 区分后付费和包年包月；
3. 统计每个产品每月的消费金额；
4. 对后付费产品统计每月计费项、用量、用量单位和消费金额；
5. 展示产品及计费项的月度费用、用量趋势；
6. 生成可验证、可追溯的 Excel 报告。

非核心任务：

- 判断实例是否闲置；
- 判断实例是否应升配或降配；
- 自动选择资源包或购买规格；
- 承诺优化后的节省金额；
- 使用大模型直接计算原始账单。

模型可以对已经验证的汇总结果提供参考性观察，但不得将其描述为确定的优化结论。

## 2. 使用方式

保留两种入口，共用同一套字段模型、校验、聚合和报告逻辑。

### 2.1 默认入口：客户导出账单文件

适用于大多数一次性分析。

流程：

1. 客户从阿里云费用与成本控制台导出计费项级账单；
2. 客户将 CSV、XLSX、ZIP 或多个月份文件交给售后；
3. 售后在对话中上传文件并指定分析账期；
4. Skill 运行确定性解析、校验、聚合和报告生成程序；
5. 校验通过后返回 Excel 报告。

原始文件只读，不覆盖、不删列、不原地修改。

### 2.2 补充入口：AK/SK 拉取

适用于客户不方便导出文件或需要补齐账期的情况。

交互方式：

1. 客户直接将项目临时 AK/SK 提供给售后；
2. 售后将 AK/SK、客户名称和分析账期一次性粘贴到当前对话；
3. Skill 从对话中提取参数并调用账单 API；
4. 确认信息只显示 AK 末四位，不复述完整 AK/SK；
5. 成功或失败后提醒客户禁用并删除该 AK。

不依赖密码平台。AK/SK 只用于当次执行，不写入配置、报告、中间文件和普通日志。

### 2.3 统一原则

- 文件入口优先；
- API 入口为补充能力；
- 两种入口都转换为同一个 `BillRecord`；
- 两种入口必须生成一致口径的报告；
- 同一账号、同一账期的数据通过两种入口获取时，应能完成差异核对。

## 3. 输出报告定稿

正式报告包含四个 Sheet。

### 3.1 Sheet 1：账单分析

回答：

- 客户使用了哪些产品；
- 每个产品属于后付费、包年包月还是其他费用；
- 每个产品每月消费多少钱；
- 每种计费方式及全部产品合计多少钱。

建议布局：

| 计费方式 | 产品Code | 产品名称 | 月份1 | 月份2 | … | 合计 |
|---|---|---|---:|---:|---:|---:|

要求：

- 月份按时间升序；
- 分计费方式显示小计；
- 最后一行显示总计；
- 不再保留“优化方案报价”“节省费用/年”等无法由账单确定的核心列。

### 3.2 Sheet 2：后付费分析

回答：

- 每个后付费产品包含哪些计费项；
- 每个计费项每月产生多少用量；
- 每个计费项每月产生多少费用；
- 整个账期的累计用量和累计费用是多少。

建议布局：

| 产品Code | 产品名称 | 计费项Code | 计费项名称 | 地域 | 用量单位 | 月份1用量 | 月份1费用 | 月份2用量 | 月份2费用 | … | 总用量 | 总费用 |
|---|---|---|---|---|---|---:|---:|---:|---:|---:|---:|---:|

聚合键至少包含：

```text
product_code
+ item_code
+ usage_unit
+ region（启用地域维度时）
```

禁止跨用量单位合并。例如 GB、GB-Month、次、小时不能合并成同一个“总用量”。

### 3.3 Sheet 3：趋势分析

确定性生成以下趋势：

- 每月总费用；
- 后付费与包年包月月度费用；
- 各产品月度费用；
- 后付费产品下各计费项月度费用；
- 后付费计费项月度用量。

图表默认只展示按费用排序的前 N 个产品或计费项，完整数据保留在表格中。N 作为配置项，默认值建议为 10。

趋势只描述变化，不自动解释为扩容、闲置、异常或业务增长。

### 3.4 Sheet 4：数据说明

至少包含：

- 数据来源：文件或 API；
- 客户名称；
- 账号范围；
- 分析账期；
- 是否包含未结束月份；
- 原始文件名、文件 SHA-256 和 Sheet；
- 原始行数、成功解析行数、异常行数；
- 重复文件数、重复记录数；
- 字段映射版本和解析器版本；
- 币种；
- 原始金额、标准数据金额、报告金额及差异；
- 用量缺失记录数；
- 未知费用类型和未知字段；
- 最终校验状态及警告。

## 4. 字段白名单

字段分为“业务计算字段”“技术校验字段”和“可选维度”。大模型只接收聚合结果，不接收这些原始明细行。

### 4.1 核心业务计算字段

| 阿里云原始字段 | 标准字段 | 必需性 | 用途 |
|---|---|---|---|
| 账单信息/账单月份 | billing_month | 必需 | 月度聚合 |
| 账单信息/费用类型 | billing_type_raw | 必需 | 区分后付费、包年包月及其他费用 |
| 产品信息/产品Code | product_code | 必需 | 产品稳定聚合键 |
| 产品信息/产品名称 | product_name | 必需 | 报表展示 |
| 产品信息/计费项Code | item_code | 后付费必需 | 计费项稳定聚合键 |
| 产品信息/计费项名称 | item_name | 后付费必需 | 报表展示 |
| 应付信息/应付金额（含税） | payable_amount | 必需 | 消费金额 |
| 用量信息/用量 | usage | 字段必需、值可空 | 后付费月度用量 |
| 用量信息/用量单位 | usage_unit | 字段必需、值可空 | 用量分组和展示 |

说明：

- `用量`和`用量单位`列必须存在，但部分行允许为空；
- 两者同时为空时记录警告，不把空值转换为零；
- 只有一个为空时标记为数据异常；
- 空用量记录仍参与金额汇总，但不参与用量合计。

### 4.2 可选分析维度

| 阿里云原始字段 | 标准字段 | 使用条件 |
|---|---|---|
| 资源信息/地域Code | region_code | 需要按地域分析时作为稳定键 |
| 资源信息/地域 | region_name | 需要按地域分析时用于展示 |
| 账单信息/交易类型 | transaction_type | 需要区分新购、续费、退款、退订或调账时 |

第一版可以默认保留地域维度，但地域缺失不得影响产品和计费项费用汇总。  
`交易类型`不能替代`费用类型`判断后付费和包年包月。

### 4.3 技术校验字段

这些字段不进入业务分析表，但解析和校验阶段必须读取。

| 阿里云原始字段 | 标准字段 | 用途 |
|---|---|---|
| 标识信息/账单明细ID | line_item_id | 记录唯一性和重复检测 |
| 身份信息/资源购买账号ID | account_id | 验证客户账号范围 |
| 定价信息/定价币种 | currency | 防止跨币种直接汇总 |

程序生成以下血缘字段：

```text
source_file
source_file_sha256
source_sheet
source_row
record_hash
schema_version
parser_version
```

### 4.4 可选金额勾稽字段

如果源文件包含以下字段，校验阶段读取并用于逐行金额勾稽，勾稽完成后不进入分析模型：

- 费用信息/目录总价；
- 订阅抵扣信息/订阅抵扣目录总价；
- 优惠信息/优惠金额；
- 优惠券抵扣信息/优惠券抵扣金额；
- 优惠信息/优惠后金额。

不得为了减少列数而删除有明确校验价值的字段。字段裁剪发生在程序的标准化层，客户原始文件始终完整保留。

### 4.5 明确不需要的字段

当前核心范围不需要：

- 实例ID；
- 资源名称；
- 实例规格；
- 选型配置；
- CPU、内存或其他监控指标；
- 订单号；
- 优化报价和节省金额输入字段。

如果未来增加实例费用归集或关联云监控，应另立需求，不在本次重构中提前扩展。

## 5. 费用类型映射

使用版本化配置维护阿里云原始费用类型到标准类型的映射，不在模型提示中猜测。

标准类型：

```text
PayAsYouGo     后付费/按量
Subscription   包年包月/订阅
Other          退款、调账或其他费用
```

当前样本至少包含：

| 原始费用类型 | 标准类型 |
|---|---|
| 云资源按量费用 | PayAsYouGo |
| 订阅预付费用 | Subscription |

处理规则：

- 已知类型按映射表转换；
- 未知类型保留原值并归入 `Other`；
- 未知类型必须写入“数据说明”；
- 未知类型金额仍计入总账，不得静默丢弃；
- 未完成业务确认前，不把未知类型强行归入后付费或包年包月。

### 5.1 核心指标口径

- 账单月份以每条明细的`账单信息/账单月份`为准，不从文件名推断；
- 消费金额统一定义为`应付信息/应付金额（含税）`之和；
- 产品月度费用按`计费方式 × 产品Code × 账单月份`汇总；
- 后付费计费项费用仅汇总标准类型为`PayAsYouGo`的记录；
- 后付费计费项用量仅汇总用量非空、且产品Code、计费项Code、地域和用量单位相同的记录；
- 零金额和负金额保留在汇总中，并在数据说明中单独统计；
- 产品Code和计费项Code是分组键，名称只用于展示；
- 同一Code出现多个名称时不得拆成多个产品或计费项，选择出现次数最多的非空名称展示，并记录名称冲突；
- `product_code_map.json`只用于名称缺失时的展示补充，不得把未知产品统一归入“其他产品”；
- 所有 Sheet 使用同一份 `AnalysisResult`，不得在各 Sheet 中分别实现聚合口径。

## 6. 确定性处理流程

```text
输入文件/API响应
  → 来源识别
  → 文件哈希和账期预检
  → 表头识别与版本化字段映射
  → 流式逐行解析
  → 标准 BillRecord
  → 完整性、重复、币种和金额校验
  → Decimal 聚合
  → 独立路径交叉汇总
  → AnalysisResult
  → Excel 报告
  → Excel 回读核对
  → 可选参考说明
```

执行要求：

- 禁止让大模型读取并计算完整原始账单；
- 金额和用量使用 `Decimal`，禁止用二进制浮点数作为最终核对依据；
- CSV 和 XLSX 使用流式读取，避免把数万行全部装入模型上下文；
- 账号ID、产品Code、计费项Code和账单明细ID始终按字符串处理；
- 清理字段前后空格、制表符和不可见字符，但保留原始值用于追溯；
- 任一行解析失败都必须有明确错误，不允许静默跳过；
- 原始账单不复制到最终报告，避免扩大客户数据暴露范围。

## 7. 数据准确性设计

### 7.1 文件级检查

- 文件是否可以打开；
- 文件类型、编码和 Sheet 是否可识别；
- 是否为计费项明细而不是普通月度汇总表；
- 文件 SHA-256 是否与已导入文件重复；
- 账单月份是否覆盖用户指定范围；
- 是否混入其他账号；
- 是否存在多币种；
- 是否包含当前未结束月份。

当前月默认不纳入完整历史分析。用户明确要求分析当前月时允许处理，但报告必须标记“数据截至导出时间，月份未结束”，不得与完整月份直接得出增长结论。

### 7.2 行级检查

- 必需字段存在；
- 账单月份格式合法；
- 产品和计费项代码可读取；
- 应付金额可以无损转换为 `Decimal`；
- 用量可以转换为 `Decimal`或为空；
- 用量与单位满足成对规则；
- 明细ID在合理范围内唯一；
- 负金额、零金额和未知费用类型被单独计数。

### 7.3 重复处理

优先使用`账单明细ID + 账号ID`识别重复记录。

- 同一文件内ID重复：阻断；
- 多文件出现相同ID且内容完全一致：识别为重复导入，不重复计入；
- 相同ID但内容不同：阻断并输出冲突行；
- 缺少明细ID：不得自动删除外观相同的合法记录，只能使用记录哈希辅助检查并产生警告。

不得依赖实例ID去重。

### 7.4 金额和用量聚合

金额至少按以下维度分别汇总：

```text
全部记录
月份
计费方式
产品
计费方式 × 产品 × 月份
后付费产品 × 计费项 × 用量单位 × 月份
后付费产品 × 计费项 × 地域 × 用量单位 × 月份（启用地域时）
```

必须满足：

```text
标准记录应付金额合计
= 各月份金额合计
= 各计费方式金额合计
= 各产品金额合计
= Sheet 1 总计
```

后付费部分必须满足：

```text
后付费标准记录金额
= 后付费计费项月度金额
= Sheet 2 总费用
= Sheet 3 后付费费用趋势合计
```

用量只能在产品、计费项、地域和用量单位一致时相加。金额可以合计，用量单位不一致的用量不得合计。

### 7.5 双路径交叉校验

建议保留两条独立计算路径：

1. Python `Decimal` 分组聚合；
2. SQLite 导入标准记录后使用 SQL 聚合。

两条路径的行数、月份、产品、计费方式、计费项和金额必须一致。最终 Excel 生成后重新读取关键单元格，与 `analysis-result.json` 比较。

双路径不能共用同一个聚合结果对象，否则无法发现聚合逻辑错误。

### 7.6 精度和展示

- 内部结果以 Decimal 字符串保存；
- 不在逐行阶段四舍五入；
- Excel 单元格写入数值，展示格式与底层精度分离；
- 数据说明 Sheet 记录金额精度和最终舍入规则；
- 所有差异校验在展示格式化之前完成。

## 8. 大模型职责边界

### 8.1 模型可以做

- 根据已验证汇总解释客户主要费用构成；
- 描述某产品或计费项费用、用量的月度变化；
- 标记需要售后进一步调查的高费用或明显变化项；
- 提供一般性的参考检查方向。

### 8.2 模型不能做

- 对原始账单逐行求和；
- 修改程序计算结果；
- 根据账单判断实例闲置；
- 根据账单判断CPU或内存是否需要升降配；
- 自动推荐确定的资源包规格；
- 生成未经验证的节省金额；
- 将缺失用量补成零；
- 把趋势变化直接解释为业务增长或资源浪费。

### 8.3 参考建议的实现顺序

参考建议不属于第一版验收范围，建议作为后续可选能力：

1. 程序先生成有证据编号的事实，例如高费用产品、环比变化和用量变化；
2. 模型只接收这些事实和数据质量说明；
3. 每条参考建议必须引用证据编号；
4. 输出统一标记“仅供参考，需要结合合同、产品定价和业务情况确认”；
5. 关闭模型建议时，核心四个 Sheet 仍能完整生成。

## 9. 标准数据模型

建议定义：

```python
BillRecord(
    billing_month,
    billing_type,
    billing_type_raw,
    product_code,
    product_name,
    item_code,
    item_name,
    payable_amount,
    usage,
    usage_unit,
    region_code=None,
    region_name=None,
    transaction_type=None,
    line_item_id=None,
    account_id=None,
    currency=None,
    source_file=None,
    source_sheet=None,
    source_row=None,
)
```

API 和文件入口只负责生成 `BillRecord`，不得分别实现两套聚合逻辑。

## 12. 机器可读产物

每次分析在临时运行目录生成：

```text
manifest.json
validation.json
analysis-result.json
report.xlsx
```

内容：

- `manifest.json`：输入文件、哈希、账期、账号、行数、版本；
- `validation.json`：字段、重复、币种、金额和聚合校验；
- `analysis-result.json`：Excel使用的唯一事实来源；
- `report.xlsx`：交付给售后的正式报告。

这些文件不得包含 AK/SK。

命令最后一行输出统一 JSON：

```json
{"status":"ok","report_path":"...","validation_status":"passed"}
```

失败：

```json
{"status":"failed","code":"VALIDATION_FAILED","validation_path":"..."}
```

## 13. 测试方案

### 13.1 解析测试

- 阿里云消费明细账单 V2 XLSX；
- UTF-8、UTF-8 BOM、GB18030 CSV；
- ZIP、目录和多月份文件；
- 大文件流式读取；
- 61列原始账单裁剪为标准字段；
- 字段顺序变化；
- 表头别名和版本变化；
- 数字、文本、科学计数法和尾部制表符；
- 空文件、损坏文件和错误 Sheet。

### 13.2 数据质量测试

- 缺少账单月份；
- 缺少应付金额；
- 用量和单位同时为空；
- 用量和单位仅一项为空；
- 重复文件；
- 文件内重复明细ID；
- 相同ID内容冲突；
- 多账号混入；
- 多币种混入；
- 负金额、零金额、退款和调账；
- 当前月部分账单；
- 未知费用类型。

### 13.3 聚合测试

- 后付费与包年包月月度金额；
- 产品月度金额；
- 后付费计费项月度金额；
- 后付费计费项月度用量；
- 同一计费项存在多个用量单位；
- 地域维度开启和关闭；
- Decimal 高精度金额；
- Python 与 SQLite 聚合一致；
- Excel 回读与 `analysis-result.json` 一致。

### 13.4 文件与API一致性测试

准备同一账号、同一账期的脱敏文件 fixture 和 API fixture，验证：

- 月份集合一致；
- 产品集合一致；
- 计费方式一致；
- 产品月度金额一致；
- 后付费计费项月度金额和用量一致；
- 总金额一致。

如果控制台文件与 API 存在天然口径差异，必须写入 `report-schema.md`，不得静默修正。

### 13.5 当前真实样本的使用

现有 `local-fixtures/1464150682107048-20260722092352_202607_consumedetailbillv2.xlsx` 可用于本地字段和大文件回归：

- 61个原始字段；
- 4,252条明细；
- 10个候选分析字段均存在；
- 用量和用量单位存在部分空值；
- 账单明细ID可用于唯一性校验。

该文件属于未结束月份的导出数据，只能验证解析和字段口径，不能作为完整月趋势基准。正式发布 Skill 前，应替换为脱敏测试数据，避免把真实客户账单打包发布。

## 14. 分阶段实施

### 阶段一：范围、字段和报告口径定稿

交付：

- `bill-schema-v2.json`；
- `billing-type-map.json`；
- `report-schema.md`；
- 精简后的 `SKILL.md`；
- 更新后的 `agents/openai.yaml`。

验收：

- 核心输出不再包含确定性优化结论和节省金额；
- 后付费/包年包月只由版本化费用类型映射产生；
- 业务字段、校验字段和可选字段边界清楚。

### 阶段二：文件入口与确定性分析

交付：

- XLSX/CSV 文件解析；
- 标准 `BillRecord`；
- 完整性、重复、币种和金额校验；
- 产品、计费方式和计费项月度聚合；
- `analysis-result.json`。

验收：

- 数万行账单不进入模型上下文；
- 原始行数等于成功解析行数；
- 无静默跳过；
- 多维金额核对差异为零；
- 用量缺失不会被误算为零。

### 阶段三：Excel 报告

交付：

- 账单分析；
- 后付费分析；
- 趋势分析；
- 数据说明；
- Excel回读校验。

验收：

- 四个 Sheet 均可直接用于售后分析；
- 每月产品金额、后付费计费项用量和费用完整；
- Sheet之间的金额可以相互核对；
- 大文件输出可正常打开，表头、金额和图表不截断。

### 阶段四：API入口

交付：

- 账单只读 API 拉取；
- 售后在对话中一次性提供 AK/SK；
- 分页、跨月、失败重试和月份完整性处理；
- 文件与 API 同口径测试；
- 凭据脱敏和回收提示。

验收：

- AK/SK 不写入配置、中间文件、报告或普通日志；
- 任一月份拉取失败时不生成完整报告；
- API 与文件入口使用同一个分析器和报告生成器。

### 阶段五：参考建议与发布清理

交付：

- 可关闭的参考观察模块；
- 证据编号和模型输出校验；
- 脱敏测试 fixture；
- `.gitignore`；
- 清理 venv、缓存、历史输出、真实配置和废弃脚本；
- Skill 结构校验和跨平台测试。

验收：

- 关闭模型能力不影响核心报告；
- 每条参考观察都有已验证数据依据；
- 报告明确标注建议仅供参考；
- 发布包不包含客户账单、真实凭据和历史报告。

## 15. 阻断和警告规则

### 15.1 阻断

以下情况不生成正式分析报告：

- 文件无法解析；
- 指定账期完全缺失；
- 必需字段缺失；
- 应付金额存在不可解析值；
- 多币种无法分开；
- 明细ID冲突；
- 重复数据无法判断；
- 原始金额、标准金额和报告金额不一致；
- Python与SQLite关键聚合结果不一致；
- API 任一指定月份拉取失败。

### 15.2 警告

以下情况允许生成报告，但必须写入“数据说明”：

- 当前月份尚未结束；
- 部分行用量和单位同时为空；
- 地域缺失；
- 交易类型缺失；
- 未知费用类型已归入 Other；
- 存在负金额或零金额；
- 缺少可选金额勾稽字段；
- 缺少明细ID但不存在可证明的重复记录。

## 16. 最终验收标准

- [ ] 默认支持客户上传 XLSX/CSV 账单；
- [ ] 支持多文件和多月份；
- [ ] 支持售后在对话中一次性提交 AK/SK；
- [ ] 文件和 API 共用同一个标准模型、校验器、分析器和报告生成器；
- [ ] 账单月份、费用类型、产品、计费项、用量、单位和应付金额映射明确；
- [ ] 能准确列出客户使用的产品；
- [ ] 能按后付费和包年包月统计每个产品每月费用；
- [ ] 能统计后付费产品每个计费项每月用量和费用；
- [ ] 能生成产品及计费项月度趋势；
- [ ] 不跨单位合计用量；
- [ ] 不把空用量当作零；
- [ ] 不静默丢弃异常行；
- [ ] 原始记录、标准记录、各维度聚合和Excel金额一致；
- [ ] 报告包含完整数据质量说明；
- [ ] 模型不直接计算原始账单；
- [ ] 模型不根据账单判断闲置或升降配；
- [ ] 模型不承诺节省金额；
- [ ] 参考建议可以完全关闭；
- [ ] 发布包不包含真实账单、真实AK/SK、缓存和历史输出。
